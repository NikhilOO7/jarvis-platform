01 · Orientation

What JARVIS Is & How To Read This Book

JARVIS is a personal AI operating system: it captures everything its operator chooses to feed it (links, notes, social saves, chats, videos), turns that pile into structured, searchable memory, and then acts on natural-language commands through agent workflows — with approval gates in front of anything risky, and a presence layer that reaches the browser, Telegram, and a cinematic web HUD.

Foundations — what "personal AI OS" actually means An operating system schedules programs over hardware. JARVIS schedules intelligence over a person's digital life: memory (what you saved), cognition (models reasoning over it), hands (tools that do things), and senses (capture surfaces). The analogy is load-bearing — you will see kernels (the executor), syscalls (the tool registry), permissions (approval gates), and device drivers (connectors) throughout.

The seven pillars — the product's north star

Every feature in this codebase maps to one of seven capability pillars. When a proposed feature maps to none, it gets cut. This is the first CTO lesson: a small system that knows what it is beats a big system that doesn't.

#Pillar"Movie moment"Engineering reality
1Total recall"Pull up everything on Project Atlas"Ingestion + pgvector semantic memory + knowledge graph
2Natural command"Run a diagnostic"LLM intent router → workflow runs; chat with citations
3Real agencyDraft and carry out approved workTool-calling executor; draft-artifact connectors
4Judgment & safety"Sir, I must advise against this"Risk scoring, approval gates, audit logs

How to read this book — three passes

Pass 1 · The Map (ch. 1–5)

Read for shape, not detail. After pass 1 you should be able to draw the system from memory on a whiteboard and name why each technology was chosen.

Pass 2 · The Machinery (ch. 6–15)

Each chapter is one subsystem: what it does, why it exists, how it works step-by-step, where it breaks, and what we deliberately did NOT build. Read with the code open.

Pass 3 · The Judgment (ch. 16–21)

Cross-cutting concerns and the decision frameworks behind them. This is where engineering becomes architecture, and architecture becomes strategy.

CTO lens — the meta-pattern of this whole book Every subsystem here answers five questions: WHAT does it do, WHY does it exist (what breaks without it), WHEN does it run (its triggers and lifecycle), HOW does it work (the mechanism), and WHAT WAS TRADED (the alternatives we rejected and the debt we accepted knowingly). If you internalize one habit, make it this: never present a design without its rejected alternatives. A design without named trade-offs is a design you don't understand yet.

The honest-engineering rule

This codebase has one cultural law that appears in every chapter: the UI never lies. Early versions showed fake CPU gauges, a hardcoded "gpt-4o" badge, and invented run counts. All were replaced with real values or removed. Fake telemetry is a small sin that metastasizes: the day your dashboard mixes real and invented numbers is the day nobody can trust any number on it. Offline modes say "OFFLINE"; unsaved results say "NOT SAVED (no database)".

02 · Product Thinking First

The Problem, The User, and Why This Shape

Great architecture starts as product reasoning. Before a single table existed, three product decisions fixed the entire technical shape of JARVIS: who it serves, what loop it closes, and what it refuses to do.

The problem statement

People save enormous amounts of content — Instagram reels, LinkedIn posts, bookmarks, exports, chats — because it might matter later. Saved content then becomes a graveyard: unstructured, unconnected, undeduplicated, unactionable. The pain is not capture; capture is easy. The pain is that captured information never becomes a decision. JARVIS exists to close that loop: every captured item should eventually answer "why did this matter, what is it related to, and what should I do about it?"

Decision 1 — Single operator, not SaaS

JARVIS optimizes for one power user before general polish. It has optional single-operator passphrase sessions, but no tenancy or billing. This keeps the private-alpha boundary explicit without pretending the product is multi-user ready.

Decision 2 — Local-first

Your memory lives in your Postgres on your machine. Model API calls are the only data that leaves. This one choice reframes security (ch. 9), infra (ch. 18), and trust: JARVIS is a butler in your house, not a service you visit.

Decision 3 — Explicit capture only

No stealth scraping, no private-API reverse engineering, no background collection. Everything enters through an act of user intent: a save, an upload, an approval click. This is both an ethics position and a durability position — scrapers break and get you banned; consent-first surfaces don't.

Decision 4 — Degrade gracefully, fail closed

Read and routing paths can use deterministic fallbacks. Missing storage produces explicit offline or parse-only state; missing cognition blocks execution with a FAILED run. The UI remains explorable without presenting fabricated records or simulated completion.

CTO lens — one-way doors vs two-way doors Amazon's framing, and the sharpest product-architecture tool you'll ever use. A two-way door is reversible — walk through, look around, walk back (a UI layout, a prompt, a cron schedule). A one-way door is expensive to reverse (your database engine, your tenancy model, publishing data to a third party, an API contract others build on). Spend decision energy proportionally: two-way doors get minutes, one-way doors get design docs. In JARVIS: Postgres+pgvector was a one-way door (all retrieval, dedupe, and graph code assume it); the keyword router was a two-way door (we later swapped in an LLM router in an afternoon — because the interface stayed stable).

Why "workflows with approval gates" is the core product object

An assistant that can only chat is a toy; an assistant that acts without oversight is a liability. The product thesis of JARVIS is the middle path: agency under contract. Commands become runs — inspectable, loggable, cancellable objects — and risky steps arm approval gates that a human clears. That single product idea generates most of the schema (ch. 5), the executor (ch. 8), and the safety model (ch. 9). When you find the load-bearing product object, the architecture mostly draws itself.

War story — the fake APPROVE button An early build shipped an APPROVE / REJECT button pair in the command console with no onClick. It looked finished; it did nothing. Worse, a risk label compared "high" === "HIGH" — always false — so every command rendered as low-risk green. Two lessons: (1) dead UI is worse than no UI, because it trains users to distrust controls; (2) case-sensitivity bugs in safety-critical display paths are not cosmetic bugs. Both were found by reading the code path end-to-end, not by testing happy paths.

The roadmap as a dependency graph, not a wishlist

The master plan phases — engine → memory → presence → hands → proactivity → orchestration → ambience — are ordered by dependency, not excitement. Presence (Telegram) reuses the engine; proactivity reuses presence; orchestration reuses everything. Each phase is independently shippable and demoable. A roadmap whose phase N+1 doesn't consume phase N's output is just a list of hopes.

03 · High-Level Design

The Whole System On One Page

Hold this diagram in your head and every later chapter becomes a zoom-in. Six layers: presence (how you reach JARVIS), cognition (how it decides), memory, safety, action, and proactivity. One database. One process — on purpose.

Why a monolith — and why that's the senior answer

Why one process A single Next.js app owns UI, API, and execution. Function calls instead of network calls means no serialization bugs, no partial deploys, no distributed tracing needed to debug a request, and refactors that are project-wide-rename cheap. The moment of truth: the executor runs inside a route handler. That is a known, accepted limitation (a long run ties up a request) with a designed escape hatch — the executor's only contract with the world is executeWorkflowRun(runId), so lifting it into a worker process later changes one call site, not the architecture.
Trade-off ledger — monolith edition Accepted: runs block a request thread (capped by maxDuration); a crash mid-run leaves a RUNNING row (mitigated: logs show last step; a janitor job is a listed follow-up); horizontal scale requires extraction later. Rejected alternative: microservices on day one — would have cost weeks of infra for a single-user product with zero throughput problems. Rule of thumb: services are an organizational scaling tool as much as a technical one. You extract a service when a team, a failure domain, or a scaling curve demands it — not before. Ch. 19 shows the exact seams.

The four request lifecycles

Everything the system does is one of four shapes. Chapters 6–14 are these four shapes in detail:

① Capture

Content in → normalize → dedupe → enrich (classify/summarize) → knowledge + vectors + graph. Synchronous, idempotent-by-hash, degrade-to-heuristics.

② Command

Utterance in → route → run object → (gates?) → executor tool-loop → output + audit log. The only shape that does things.

③ Question

Query in → semantic retrieval → grounded generation → cited answer, persisted. Read-only, safe everywhere (HUD, panel, Telegram).

④ Schedule

Clock in → deterministic run creation → shape ② without a human utterance. Proactivity is just a command with a cron for a mouth.

05 · Data Model

The Schema — Thirteen Models, Every Field Justified

The schema is the constitution: everything else is code that can be rewritten Tuesday. These 13 models split into two cores — the knowledge core (what JARVIS remembers) and the automation core (what JARVIS does) — plus connective tissue. Read this chapter slowly; every later system is just verbs on these nouns.

The knowledge core, model by model

RawSourceItemthe immutable inbox — every capture, verbatim
What
One row per capture event: manual link, pasted text, export row, extension grab, video transcript. Keeps original URL, raw text, platform, author, and a rawMetadata Json escape hatch.
Why
Separation of evidence from interpretation. AI enrichment will improve; when it does you can re-derive every KnowledgeItem from untouched raw sources. Destroying raw input to store only the summary is the classic irreversible mistake.
Keys
contentHash (SHA-256 of canonical-url+title+text) and canonicalUrl (tracking params stripped, hash removed) — the dedupe double-lock, both indexed. duplicateOfId is a self-relation: duplicates are recorded, not rejected, so "you saved this 3 times" is itself queryable signal.
Trade-off
Raw text bloats the table; acceptable at personal scale, and it's the archival layer — cold storage offload is the ch. 19 answer, not deletion.
KnowledgeItemthe derived, useful memory — what retrieval actually searches
What
Title, summary, category enum, insights[], actions[], confidence float, and an embedding vector(1536).
Why
Search should rank meaning, not raw noise. Raw text is evidence; KnowledgeItem is testimony. The split also means re-enrichment (better prompts later) rewrites this table without touching evidence.
How
Written by the ingestion pipeline (ch. 6); embedded at write time; queried by pgvector cosine distance (ch. 7); chipped with entities (ch. 10).
Detail
The vector column is Prisma-Unsupported("vector(1536)") — Prisma creates it in migrations but can't read it, which is precisely why all vector I/O lives in one raw-SQL module. Quarantined leak, by design.
Entity · EntityMention · EntityRelationthe knowledge graph — nouns, sightings, and co-occurrence
What
Entity is a canonical noun (typed: PERSON, PRODUCT, FOOD, WORKOUT, COMPANY…), globally unique on (type,name). EntityMention is a sighting of an entity in a knowledge item. EntityRelation is a weighted edge; today one relation kind, mentioned_with, whose weight increments every co-occurrence.
Why
Vectors answer "what's similar?"; graphs answer "what's connected?" — different questions. "What do I know about Alex" is a graph query (mentions), not a similarity query.
Why not a graph DB
Neo4j is a second system to run for what is, at this scale, three relational tables and two indexes. The graph-DB door stays open: these tables translate mechanically if traversal depth ever demands it. (Rule from ch. 4: don't add a database to avoid writing a JOIN.)
ChatSession · ChatMessageconversation persistence with provenance
What
Sessions of role/content messages; assistant rows carry metadata.sourceIds — which knowledge items grounded that answer.
Why provenance
A memory system that can't show its work isn't trustworthy. Storing citation IDs per answer makes "why did you say that?" answerable forever, and later enables click-through from an answer to its evidence.

The automation core, model by model

WorkflowTemplate → WorkflowRun → ApprovalRequestthe product's spine: agency under contract
What
Templates define reusable step lists (steps Json: title, description, approvalRequired). A Run is one execution: command, status FSM (QUEUED → RUNNING → COMPLETED/FAILED, plus WAITING_FOR_APPROVAL/CANCELLED), input/output/logs Json. ApprovalRequests are per-gate rows with their own FSM and decidedAt.
Why runs are rows
Anything important enough to execute is important enough to inspect, audit, resume, and cancel. Ephemeral in-memory jobs die with the process and take their story with them.
Why logs are Json
Honest trade-off: appending logs into a Json column is simple and reads with the run in one query — but it can't be indexed/aggregated ("all TOOL_CALL failures this week") and the naive Prisma logs: {push} operator doesn't even work on Json columns (a real production bug, ch. 9). The normalization threshold is written down in advance: when logs need cross-run queries or exceed ~1MB/run, promote to a RunEvent table. Deliberate debt with a tripwire beats accidental debt every time.
Concurrency
Run claiming is an atomic compare-and-swap: updateMany({where:{id,status:"QUEUED"},data:{status:"RUNNING"}}) — count 0 means someone else won. This single line makes triple-trigger execution (approval hook + manual button + command route) safe without locks. Ch. 8 dissects it.
AgentDefinition · ConnectorConfigregistries — one dormant by design, one carrying secrets
What
AgentDefinition is the future DB-driven agent registry (today agents live in code — the table waits for user-defined agents). ConnectorConfig stores per-connector state and scopes; its first real tenant is the extension pairing token in metadata.
Lesson
Schema can lead code when migration cost is high and the shape is certain — but track dormant tables explicitly, or they become archaeology. Both of these are named in the master plan with their activation phase.
CTO lens — four schema rules that age well (1) Enums for state machines — a status column typed as free text will eventually contain "done", "Done", and "DONE ✅". (2) Index what you filter, and nothing else — every index taxes every write; JARVIS indexes status, category, hash, URL because pages filter on exactly those. (3) Json columns are for payloads you read whole, never filter by — the moment a query wants WHERE json→…, normalize. (4) Store evidence separately from interpretation — the raw/derived split is what makes every future re-enrichment, migration, and "oops" recoverable.
06 · The Mind, Part 1

The Ingestion Pipeline — Content Becomes Memory

Every capture surface — save form, export upload, browser extension, Telegram /save, video transcript — funnels into one function: ingestItem() in src/lib/ingestion.ts. One pipeline means one place for dedupe, one place for enrichment, one place to improve. This is the most-reused 100 lines in the codebase.

Normalize the URL. hash.ts · normalizeUrl()
Strip the fragment and tracking params (utm_* etc.) to produce canonicalUrl. The same article shared from three apps arrives with three different URLs; canonicalization makes them one identity. Why first: every later step keys off identity.
Hash the content. hash.ts · stableHash()
SHA-256 over canonicalUrl + title + text → contentHash. Content-addressing 101: identical input, identical fingerprint, regardless of when or from where it arrives.
Check for duplicates — then record, don't reject.
Find any existing row matching hash OR canonical URL. On a hit, a new row is still written with status: DUPLICATE and duplicateOfId pointing at the original. The capture event is real signal ("saved 3×" = importance); only the enrichment cost is skipped. This is also what makes every import resumable: re-upload a 500-item export, the 400 already processed short-circuit for free.
Classify + summarize, in parallel. ai/classify.ts · ai/summarize.ts
Promise.all because they're independent — pipeline latency is the max, not the sum. Each has a deterministic fallback (keyword map / truncation) so ingestion works with zero API keys, just worse.
Derive the KnowledgeItem. ai/knowledge.ts
Title + summary + category + starter insights/actions, nested-created with the raw row in one Prisma write — evidence and testimony born in the same transaction.
Embed. ai/retrieval.ts · storeItemEmbeddings()
One embedding call over title+summary+text (8k-char cap), written to BOTH raw and knowledge rows via raw SQL UPDATE … SET embedding = $1::vector. Non-fatal on failure — an unembedded item is degraded, not lost, and keyword fallback still finds it.
Extract entities → grow the graph. ai/entities.ts · ai/knowledge-graph.ts
Typed entities (≤8) upserted canonically, mention edges written, co-occurrence weights incremented. Also non-fatal. Ch. 10 dissects it.
Why enrichment failures never fail ingestion The pipeline's contract is: if we accepted your capture, we saved your capture. Classification, summarization, embedding, and entity extraction are quality-of-memory, not existence-of-memory. Each is wrapped so the worst case is a plainer row. Users forgive a rough summary; they never forgive a silently swallowed save.
Failure modes & current answers LLM outage mid-pipeline: fallbacks engage (keyword classify, truncated summary), item lands as PROCESSED-but-plain; no retry queue yet — re-enrichment is a listed Phase 2 follow-up. Same content, different text snippets: hash differs → duplicate slips through; the real fix is semantic near-dup detection via embedding distance (designed, not yet built — the last Phase 2 item). Huge pastes: caps at every stage (6k classify, 8k embed, 20k stored text) keep cost and latency bounded; overflow is truncated, never errored.
CTO lens — idempotency is a product feature wearing infra clothes "Safe to retry" sounds like plumbing until you watch a user re-upload an export because they weren't sure it worked. Content-hash idempotency converts user anxiety into a no-op. Design every write path so that doing it twice is harmless, and half your error-handling UI disappears.
07 · The Mind, Part 2

Semantic Memory & RAG — The Honest Version

"Semantic search" is three ideas stacked: meaning can be a vector, closeness of vectors approximates closeness of meaning, and a database can sort by closeness fast. JARVIS implements the honest, minimal version of the stack — and documents exactly where it's naive, because knowing where your RAG is weak is the senior skill.

Foundations — embeddings in four sentences An embedding model maps text to a point in high-dimensional space (here: 1,536 numbers via text-embedding-3-small) such that texts humans consider related land near each other. "High-protein dinner ideas" and a saved recipe reel end up neighbors even though they share almost no words. Distance is measured by cosine (angle between vectors); pgvector's <=> operator returns it. That's the entire trick — everything else is retrieval engineering.
retrieval.ts · the one raw-SQL quarantine zone -- similarity search (cosine distance; 1 - distance = score) SELECT id, title, summary, category::text, insights, actions, 1 - (embedding <=> $query::vector) AS score FROM "KnowledgeItem" WHERE embedding IS NOT NULL ORDER BY embedding <=> $query::vector LIMIT $k; -- ladder: vector → keyword ILIKE terms → recent items (never returns "error")

Fig 7.1 — the fallback ladder is the design: every rung degrades quality, none degrades availability.

The grounding contract

One shared helper — getGroundingContext(question) — feeds every answer surface (HUD chat, companion Ask panel, Telegram). It returns matches plus the retrieval mode used, and that mode is passed into the prompt and back to the UI. The model is told whether its context came from semantic search or just recency; the user sees citations either way. Grounding you can't audit is vibes.

Trade-offs we're consciously carrying No chunking: items embed whole. Fine for reels and notes; long articles will need chunk-level embeddings + a parent pointer. No reranker: raw cosine order, no cross-encoder second pass. Cheap and decent at 10³ items; revisit at 10⁵. Exact-scan search: no HNSW/IVFFlat index yet — a sequential scan over one person's knowledge is milliseconds; the index DDL is a ch. 19 one-liner when row counts demand it. Query = question verbatim: no HyDE/expansion. Listed, not built. Every one of these is a two-way door — which is why shipping the naive version first was correct.
CTO lens — RAG quality is an eval problem, not a vibes problem The failure mode of every RAG system: it demos great and degrades silently. The counter-weapon is a tiny eval set — 30 real questions with known-relevant item IDs, scored recall@k on every retrieval change (ch. 16). You cannot improve what you don't measure, and with retrieval you can't even see regressions without measuring.
08 · The Mind, Part 3

The Agent Engine — Commands Become Actions

This is the heart: the subsystem that turns "draft a reply to the client" into routed intent, an inspectable run, cleared gates, a tool-calling loop, and an audited result. Three modules: the router (command-router.ts), the tool registry (agents/tools.ts), and the executor (agents/executor.ts).

8.1 The intent router — LLM judgment, keyword spine

Primary: LLM classification

routeCommandSmart() shows the model the workflow catalog (key, agents, risk, description) and demands strict JSON: {workflowKey, agentKind, confidence, rationale} — response_format: json_object, temperature 0, zod-parsed, enum-checked. Unknown workflow key? Fall through. Malformed JSON? Fall through.

Fallback: keyword scoring

The original router — substring hit-counts per workflow keyword list, a confidence curve, a briefing default. Worse at nuance, but deterministic, free, and offline. Every route result carries routedBy: "llm" | "keywords" and the console displays it — the honesty rule again.

Why keep the dumb router forever It's the engine's availability floor. LLM down, key missing, JSON garbled — commands still route. The architectural pattern is "smart path, dumb spine": ambitious capability wrapped around a boring guarantee. You'll meet it again in retrieval (ch. 7) and classification (ch. 6).

8.2 The tool registry — capability as data

A tool is a typed object: name, model-facing description, JSON-Schema parameters, a risk level, and an execute() that zod-parses its args. The registry compiles to OpenAI function specs via one mapper, and executeTool() is the single choke point where every invocation is validated, executed, and logged. Nine tools today in three families:

FamilyToolsRiskNote
Memorysearch_knowledge · save_knowledge_note · explore_entity · get_briefing_snapshot · list_recent_runslowRead/write against the operator's own database only.
Deterministiccalculate · get_current_timelowThe calculator is a hand-written recursive-descent parser — never eval(). LLM-supplied strings are untrusted input, full stop.
External-effectdraft_email · propose_calendar_event · record_expensehigh/medDraft-artifact pattern: they produce reviewable artifacts, never real sends. The tool's own description tells the model "this never sends" — honesty extends into the prompt space.
CTO lens — the draft-artifact pattern is how you ship agency early The naive ladder is "no email tool → (someday) email tool that sends." The senior ladder inserts a rung: a tool that produces the artifact of the action for human review. You get 90% of the user value (the drafting was the work!), zero blast radius, and a natural upgrade path — when OAuth connectors arrive (Phase 4), "send this draft" becomes one approval-gated step appended to an already-proven flow.

8.3 The executor — the kernel

Claim atomically. updateMany({where:{id, status:"QUEUED"}, data:{status:"RUNNING"}}) — a compare-and-swap in one SQL statement. Three triggers can race (approval hook, RUNS button, command route); exactly one wins; losers get count: 0 and stand down. No locks, no queue, no double execution.
Load run + template and verify the execution engine. Missing model configuration records EXECUTION_BLOCKED and fails the run. A configured run logs EXECUTION_STARTED with engine openai; there is no simulated-completion mode.
Walk the steps. Approval-gated steps log APPROVAL_GATE cleared (they were approved or we wouldn't be here — the executor re-asserts rather than trusts). Executable steps get a fresh model conversation: persona + command + workflow position + condensed prior-step results — each step sees a summary of history, not the full transcript. That's deliberate context-budget control.
Tool loop, bounded. Up to 6 rounds/step: model responds; tool calls are executed through the registry choke point; results return as role:"tool" messages (12k-char cap each); artifacts accumulate; every call logs TOOL_CALL name → ok|error. No tool calls → the text IS the step result. Loop exhausted → honest "hit the tool limit" result. Bounds exist because agent loops without bounds eventually find a way to spin.
Persist logs at every step boundary — a crash mid-run leaves a run whose story is readable up to the last completed step. Observability isn't a dashboard; it's writing things down as you go.
Finish with structure. output = {summary, steps[], artifacts[], engine}, status COMPLETED (or FAILED with the error in both log and output). The RUNS page renders this directly — the executor's output shape IS the UI contract.
anatomy · one step of a run (what the model actually sees) system: You are Jarvis… ground in tools… external actions only produce drafts… user: Operator command: "log a $49 SaaS receipt and remind me what I pay for" Workflow: Expense & Receipt Logger — step 2 of 3 Current step: Record expense — capture vendor, amount, category Results of prior steps: - Parse receipt: vendor=Acme, amount=49, cadence=monthly Execute this step now using tools as needed, then reply with the result. → assistant: tool_call record_expense{vendor:"Acme", amount:49, …} → tool: {"ok":true,"artifact":{"type":"expense_record",…}} → assistant: "Logged Acme at $49/mo as software; artifact filed for review." ← step result, logged
Failure modes, named Crash mid-run: row stuck RUNNING; logs show last step; janitor sweep ("RUNNING > 15min → FAILED") is the listed fix. Model returns nonsense args: zod rejects inside the tool; the model sees the error as a tool result and self-corrects — errors-as-data beats exceptions-as-control-flow in agent loops. Serverless deployment: in-request execution needs maxDuration headroom (set: 120–300s); the real fix at scale is the worker extraction (ch. 19).

Safety & Approvals — Agency Under Contract

Safety here is not a disclaimer page; it's load-bearing architecture with five interlocking mechanisms: risk levels, approval gates, audit logs, pairing tokens, and the draft-artifact rule. Together they answer the only question that matters for an agent product: what is the worst thing this system can do without me? JARVIS's answer: write rows in its own database.

The approval state machine

War story — the Prisma logs: { push } bug The original approval handler appended audit entries with Prisma's push operator — which is only valid for scalar list columns, not Json. It type-checked, it demoed (no DB in dev!), and it would have thrown on the first real approval in production. The fix reads the current logs array inside the same transaction and writes the full array back. Three durable lessons: (1) ORM operators are per-column-type — read the manual for YOUR type; (2) code that has never touched a real database is unverified code, however green the build; (3) audit-trail code deserves the most paranoid review, because it fails silently and matters most in incidents.

The five mechanisms

Risk levels

Templates and tools declare low/medium/high. Risk renders before execution (console meter, Telegram header) and decides nothing by itself — approval gates come from step declarations. Risk informs the human; gates constrain the machine; the two are deliberately independent.

Approval gates

Per-step approvalRequired becomes ApprovalRequest rows at run creation — before anything executes. Clearing the last gate is the only path from WAITING to QUEUED. The executor re-checks rather than trusts its caller.

Audit logs

Route, gate decisions, execution start, every tool call, step results, completion — all appended to the run's log with timestamps. The RUNS page renders them raw. If it isn't logged, it didn't happen; if it's logged, it can be explained.

Scoped service tokens

Extension, Telegram, worker, and cron use separate credentials with explicit route scopes, compared with crypto.timingSafeEqual. The database-minted jrv_… token remains extension-only; it is never an operator credential.

Current approval limit Approval decisions are one-way and tied to runs, but they do not yet bind an immutable action payload hash. External provider writes remain disabled until that model and its replay/idempotency tests exist.
Why constant-time comparison for a localhost token A string === leaks match-length through timing. Is that exploitable on localhost today? Almost certainly not. But auth code is copied, and copied code outlives its context — the day this app is reachable from a network, the correct habit is already in place. Security is cheapest at write time.

The Knowledge Graph — From Similar To Connected

Vectors cluster; graphs connect. After this subsystem, "creatine" seen in a reel transcript, an Instagram save, and a chat export is one node with three mention edges — and its neighbors tell you what it travels with.

Extract, typed and capped. ai/entities.ts
JSON-mode prompt over title+summary+text: at most 8 entities, valid types only (13-value enum), canonical short names ("creatine", not "creatine monohydrate supplementation"), a ≤10-word context each. zod-parsed, enum-filtered, de-duplicated case-insensitively. No key → empty array, graph stays sparse, nothing breaks.
Upsert canonically. ai/knowledge-graph.ts
Uniqueness on (type, name) is what merges cross-source sightings into one node. Upsert-don't-insert makes ingestion re-runs converge instead of fork.
Record the sighting. A mention edge (entity ↔ knowledge item), unique per pair, carrying its context sentence.
Reinforce co-occurrence. Every pair of entities in the same item upserts a mentioned_with edge with weight += 1 — IDs sorted so (A,B) and (B,A) are one edge. The graph literally strengthens with repetition, Hebbian-style: entities that fire together wire together.
Serve it. The explore_entity tool returns the node, its recent mentions (joined to knowledge items), and neighbors ranked by weight — so the agent answers "what do I know about Alex?" from structure, not similarity.
Trade-offs Pairwise edges are O(n²) per item — capped at 8 entities = ≤28 edges, bounded by design. One relation type — "mentioned_with" is co-occurrence, not semantics ("works_at", "treats", "competes_with" are future extraction targets; the schema already supports arbitrary relation strings). Name collisions — two people named Alex merge into one node until entity resolution (context-based disambiguation) exists. Known, listed, acceptable at personal scale — and a genuinely hard problem at every scale.

The HUD — A Web Interface With A Point Of View

Eleven routes, one shell, and a design system that commits to an original cinematic command-center identity. But under the command-center presentation there's disciplined engineering — server components reading Prisma directly, client islands only where interactivity demands, and a no-fake-telemetry rule with teeth.

Rendering architecture

Server components by default

Pages like /runs, /knowledge, and /approvals are async RSCs calling Prisma inline — no API hop or client cache to invalidate. Queries return observed records or explicit OFFLINE/DEGRADED/EMPTY state; they never substitute demo rows.

Client islands where users act

CommandConsole, ChatBox, forms, ApprovalActions, RunActions — local useState + fetch + router.refresh() to re-render the RSC tree. No Redux/React-Query: at this interaction density, framework state machinery would be pure overhead. State libraries are a scaling tool, not a default.

The design system as tokens

Thirteen original themes are CSS-variable palettes on body[data-theme] — glow color, accent, background depths, and presentation filters. Components never name colors; they name roles (var(--glow-rgb)). Theme switching is O(1) by construction, and the concentric signal rings, scanlines, and corner brackets all re-tint for free.

War story — the hydration mismatch The top bar generated its session ID with Math.random() at module scope. Server render produced one ID, client render another → React error #418 on every page. The fix: render a stable placeholder on the server and randomize inside useEffect, client-only. The general law: anything nondeterministic (random, Date.now, locale) must not run during SSR render — hydration demands the server and client trees match byte-for-byte on first paint.
CTO lens — cosmetic excellence is cheap; fake data is expensive The HUD spends its budget on atmosphere (a pure-CSS signal core and boot choreography) and refuses to spend it on lies (every gauge is real data or removed). Users can't tell good architecture from bad, but they can always eventually tell honest UI from theater — and so can your own engineers, which matters more.

The Browser Companion — Consent-First Capture, Listen, Watch, Ask

The most architecturally interesting subsystem: a Chrome MV3 extension that lives inside hostile territory (other people's DOMs, a service worker that sleeps, canvases that taint) and still keeps a hard promise — nothing is read until the operator approves it, item by item, on screen.

MV3 anatomy — five files, four contexts

The consent protocol

Summon. Toolbar or context menu — both are user gestures, which also grant activeTab. On non-matched sites the SW injects the content script on demand; a window flag prevents double-injection.
Propose, don't read. Adapters detect visible posts/videos (viewport-intersection + size floors) and build proposals: label, 140-char preview, and an extract() closure that runs only on approval. DM pages are special-cased: bulk proposals are refused outright; only explicit text selections appear, tagged PRIVATE CONVERSATION in amber.
Approve per item. The HUD renders in a closed shadow root (site CSS can't reach in, site JS can't query in). APPROVE runs the extraction, ships it via the SW to /api/extension/capture (Bearer token), and the row reports back ✓ SAVED or ✓ ALREADY KNOWN — dedupe surfacing all the way to the edge.
Deep dive — Listen & Watch, the hard parts Tab audio without silence: tabCapture mutes the tab for the user; the offscreen recorder pipes the stream through an AudioContext back to the speakers. Users keep hearing the reel while it records. SW lifetime: MV3 service workers idle out in ~30s; during recordings the offscreen document pings a keepalive every 20s. Frames without permissions drama: Watch mode draws the <video> element to a canvas every 3s (≤20 frames, ≤768px, JPEG q0.6) — crisp, cropped, permission-free. Cross-origin media taints the canvas and throws — caught, and the SW falls back to captureVisibleTab, which works precisely because summoning granted activeTab. Server side: Whisper transcribes; frames join the transcript in a vision prompt that must also say when frames are black (DRM) or audio is just music. Honesty in prompts, too.
Trade-off — adapters are perishable IG/FB/LinkedIn change DOMs constantly; selector-based adapters WILL rot. Mitigations: a generic adapter (og-tags/article/selection) that works everywhere as the floor, per-site adapters as progressive enhancement, and fail-soft extraction. This is a maintenance-cost decision made with eyes open: the alternative (platform APIs) simply does not exist for saves/DMs. Consent-first DOM reading at human speed is the only durable, ToS-defensible lane.

14 · The Body, Part 4

Telegram & Proactivity — Presence In Your Pocket, Then Initiative

One ~300-line zero-dependency script gives JARVIS a phone presence: grounded Q&A, command execution with inline approval buttons, capture, and — the phase-5 unlock — a scheduler that makes JARVIS speak first every morning. The design principle throughout: the bridge is a dumb pipe. All cognition stays in the app.

Why long-polling beats webhooks here

Webhooks need a public URL

JARVIS is a localhost product; exposing it means tunnels (fragile) or hosting (a different product). Long-polling (getUpdates, 30s timeout) is outbound-only: works behind any NAT, zero attack surface inbound.

The cost is latency + a daemon

Sub-second-to-seconds delivery — irrelevant for a personal assistant. The daemon doubles as the proactivity scheduler, turning its one weakness (must stay running) into its second job.

The phone approval loop — the JARVIS moment

/run draft a reply to the client → bridge relays to /api/command; router + run creation happen exactly as from the HUD. Same brain, different mouth.
Gates armed → the reply carries route metadata (agent, risk, confidence) and an inline keyboard: ◉ APPROVE / ✕ REJECT with callback_data keyed to the run; pending gate IDs held in a session map.
Tap APPROVE → bridge PATCHes each gate; the app's transaction flips the run QUEUED and after() fires the executor — the same path a HUD click takes. No Telegram-special execution logic exists.
Result comes to you. The bridge polls the runs API (3s × 20) and messages the output summary on COMPLETED — or the failure, honestly, on FAILED. Fire-and-forget becomes fire-and-report.
Why chat-id pinning is the whole auth story Until TELEGRAM_ALLOWED_CHAT_ID is set, the bridge answers any chat only with pairing instructions (your chat id, and where to put it); once set, every other chat gets silence — not even an error, because an error confirms a target exists. Two env vars (bot token, chat id) + the app pairing token = the entire perimeter.

Proactivity — the smallest possible "speaks first"

POST /api/cron/briefing (pairing-token-authed) deterministically creates and executes a briefing run — no router, no utterance, template addressed by key. The bridge computes the next JARVIS_BRIEFING_TIME occurrence and fires the endpoint on schedule, pushing the summary to the paired chat. Any external cron can hit the same endpoint — scheduler and capability are decoupled, so upgrading to EventBridge/Cloud Scheduler later (ch. 18) changes zero app code.

CTO lens — proactivity is a trust product An assistant that interrupts must be right, brief, and cancellable. Notice how conservative the design is: one scheduled message a day, at a user-chosen time, of a report the user already asked for interactively many times, with an off switch (unset the env var). Earn interruption rights slowly; you spend trust in dollars and earn it in cents.

Rung 1 — worker process, zero new infra shipped. npm run worker polls an authed claim-next endpoint (findFirst(QUEUED) → CAS claim → execute); with JARVIS_EXECUTION_MODE=worker, routes only enqueue. The CAS makes N workers safe; Postgres SKIP LOCKED is the refinement.
Rung 2 — a real queue (SQS/BullMQ) when you need rate-limits per model provider, retries with backoff, and dead-letter visibility. The run row stays the source of truth; the queue is just the doorbell.
Rung 3 — durable orchestration (Temporal-class) only when runs become hours-long, multi-day, or human-in-the-loop mid-step at scale. Expensive mental model; buy it when checkpoint/resume is a product requirement, not before.

Axis 3 — Users (the single→multi door)

Deep dive — the tenancy migration, in order (1) Auth first: NextAuth/passkey, a User table, sessions — the Phase-4 gate that was always the plan. (2) Tenant column: userId on the ~6 root models (raw items, knowledge, runs, sessions, entities…), backfilled to the founding operator; children inherit through their parent FK. (3) Enforcement in depth: every Prisma query filtered by session user (a middleware/extension makes it structural), then Postgres Row-Level Security as the belt-and-suspenders — RLS means even a forgotten WHERE clause can't leak across tenants. (4) Per-user pairing tokens (the ConnectorConfig shape already supports it) and per-user cost budgets (ch. 17). (5) The interesting product question — are entities per-user or shared? — is a privacy decision disguised as a schema decision: per-user, until an explicit sharing feature says otherwise.

Axis 4 — Model latency (the ceiling you don't own)

Every interactive path already ends at a model call; that's the floor on perceived speed. The moves, in order of leverage: streaming (SSE token-by-token for chat/console — biggest UX win per line of code), parallel tool execution where independent, prompt-cache-friendly stable prefixes, and precomputation (the briefing is already precomputed by schedule — that pattern generalizes to "prepare answers before questions").

CTO lens — capacity math before architecture debates A thousand active users × 20 captures/day = 2×10⁵ ingests/day ≈ 2.3/second — a number a single modest Postgres + a few workers handles without drama. Run the arithmetic before the architecture meeting: most scaling debates dissolve under division. The systems that die at scale usually die of unbounded tails (no caps), missing idempotency, and cross-tenant leaks — all three of which this codebase solved while it was still small. That's the actual secret: scalability is mostly hygiene adopted early, plus seams cut where the cliffs are.

Thinking Like a CTO — The Frameworks Behind Every Chapter

Strip away the code and this book has been teaching one skill the whole time: decision quality under uncertainty. Here are the ten frameworks that generated every choice in this system — named, so you can reuse them on problems that look nothing like JARVIS.

1 · One-way vs two-way doors

Reversible decisions get minutes; irreversible ones get design docs. Corollary: engineer your one-way doors into two-way doors (the provider abstraction turned "which LLM vendor" from a marriage into a fling).

2 · Find the load-bearing product object

For JARVIS it's the approval-gated run. Once found, schema, APIs, and UI all draw themselves around it. If your architecture feels arbitrary, you haven't found the object yet.

3 · Smart path, safe floor

Read and routing features sit on deterministic floors: LLM router / keyword router, vector search / keyword and recency. Action execution has a different rule: missing required cognition fails closed and is never simulated as complete.

4 · The innovation-token budget

Two exotic bets per project, everything else boring. Spend tokens where differentiation lives (agent engine, pgvector memory), never on plumbing that has a boring standard.

5 · Deliberate debt with tripwires

Debt is fine; surprise debt is not. Every shortcut in this book has a written trigger for repayment ("promote logs to a table when cross-run queries appear"). Debt + tripwire = a plan; debt alone = a time bomb.

6 · Cut seams before you need them

The executor's one-function surface, the retrieval quarantine module, the dumb-pipe bridge — each is a pre-cut extraction line. Seams cost almost nothing early and everything late.

7 · Honesty as an architectural property

Real telemetry or none; disclosed egress; explicit offline/degraded/parse-only state; graded threat models; "NOT SAVED" receipts. Trust compounds like interest, and it compounds in both directions.

8 · Idempotency & consent as defaults

Every write path retry-safe (hash dedupe, upserts, CAS claims); every capture consent-gated. These two defaults erase entire categories of both bugs and ethical incidents.

9 · Sequence by dependency, ship by phase

Engine → memory → presence → hands → proactivity: each phase consumes the last and demos alone. A roadmap is a topological sort, not a mood board.

10 · Arithmetic before architecture

Unit costs per feature, capacity math per axis, eval scores per retrieval change. Numbers dissolve most debates that opinions inflame.

Build vs buy vs wait — the third option people forget

This codebase built a CSV parser (40 lines < any dependency), bought nothing it could avoid operating (no vector DB, no queue, no graph DB — Postgres wears all three hats), and waited on everything whose forcing function hadn't arrived (auth, workers, IaC, tests-at-scale). "Wait" is not procrastination when the trigger is written down; it's inventory management for complexity. The failure mode of strong engineers is building the right thing three phases early.

CTO lens — the role, compressed A CTO's output is not code; it's the decision quality of everyone shipping code. That means: writing down trade-offs so others can extend them (this book), converting worries into graded, tracked debts, protecting the innovation-token budget from enthusiasm (including your own), and keeping one ledger nobody else keeps — the list of things that will break at the next order of magnitude, each with its rope already coiled. Founding engineers earn the title the day their pull requests start teaching.

Exercises — from reader to owner

Each exercise is scoped to teach one chapter's lesson by making you extend the real system. Do them in order; they compound like the product does.

Trace before you touch (ch. 3/6). Without running code, write the full path of a Telegram /save https://… — every file, function, and table it touches. Then verify by reading. Score yourself on what you missed.
Add a tool (ch. 8). Ship summarize_category(category): schema, zod, risk level, registry entry. Notice how much the executor did NOT need to change — that's the registry pattern paying rent.
Add an approval gate (ch. 9). Make save_knowledge_note approval-required when the note exceeds 2,000 chars. You'll discover gates are declared at run-creation, not tool-time — and why that's the safer design.
Break dedupe, then fix it semantically (ch. 6/7). Save the same article with two different snippets. Explain why hash dedupe misses it; prototype near-dup detection with embedding distance ≥ 0.95 on ingest; decide what UX a "semantic duplicate" deserves (auto-merge? flag? ask?).
Write the first real test (ch. 16). Vitest over the export parsers using the existing fixtures, including the mojibake case. Then break the IG parser deliberately and watch the test earn its keep.
Extract the worker (ch. 19, rung 1). A script that polls QUEUED, claims via the CAS, executes. Prove double-execution is impossible by running two workers against ten runs. You have now built a queue out of a WHERE clause.
Draft the tenancy PR (ch. 19). Schema diff + backfill plan + RLS policies + the entity-sharing decision memo, one page. Don't implement — the exercise is the plan, because that's the CTO deliverable.
Kill a feature (ch. 2/20). Pick any pillar and argue in one page why its next planned feature should NOT be built yet — forcing function, cost, debt, and what to do instead. Saying no with reasons is the rarest skill in this entire book.
